# Commit convention

This repository uses Conventional Commits for every human and automated commit.

## Subject format

```text
<type>(<scope>)!: <summary>
```

- `type` is required.
- `scope` is optional but preferred when it clarifies the affected boundary.
- `!` marks an intentional breaking change and requires a `BREAKING CHANGE:` footer.
- `summary` starts with a lowercase letter or digit, uses the imperative mood, contains no trailing period, and keeps the full subject at 80 characters or fewer.

The 80-character ceiling includes the type, optional scope, punctuation and summary. It
applies to both ordinary commit subjects and pull-request titles. The owner approved this
increase from 72 on 2026-09-16 so a small length overrun does not require rewriting otherwise
valid history. The generated merge/revert exceptions below remain unchanged.

## Allowed types

| Type | Use |
|---|---|
| `feat` | New externally observable behavior. |
| `fix` | Correction of incorrect behavior. |
| `docs` | Documentation-only change. |
| `refactor` | Internal restructuring without intended behavior change. |
| `perf` | Measured performance improvement. |
| `test` | Test-only or test-infrastructure change. |
| `build` | Build, packaging, or dependency mechanics. |
| `ci` | Continuous-integration configuration. |
| `chore` | Focused maintenance not covered above. |
| `style` | Formatting or whitespace only, without behavior changes. |
| `revert` | Reversal of a previous change. |

PR #24 adds the explicit `style` category for formatting-only checkpoints. It does not bypass
subject length, lowercase summary, scope syntax or the trailing-period rule. Behavioral fixes
must still use the appropriate type; semantic review is not replaced by subject validation.

## Suggested scopes

Use the smallest stable boundary, for example:

```text
repo docs api domain scheduler reconcile provider kaggle fake
store sqlite objects packaging transfer artifacts runner cli config
security tests release deps
```

New scopes are allowed when they describe a real boundary. Avoid issue numbers, personal names, or temporary branch names as scopes.

## Body and trailers

Use a body when the reason, trade-off, failure semantics, or migration impact is not obvious. Explain **what** and **why**, not a line-by-line diff. Wrap prose near 100 characters where practical.

Useful trailers include:

```text
Refs: #123
Fixes: #123
BREAKING CHANGE: describe the incompatible behavior and migration path
```

Do not add an AI model, coding agent, or assistant as an author or co-author.

## Examples

```text
docs(repo): bootstrap open-source project
feat(domain): model ambiguous submission outcomes
fix(store): retain active attempt identity after restart
test(provider): cover adapter without remote cancellation
style(acceptance): normalize whitespace
ci(repo): validate conventional commit subjects
feat(api)!: require idempotency keys for job creation
```

Breaking example:

```text
feat(api)!: require idempotency keys for job creation

Reject compute-creating requests that omit a stable idempotency key so a lost
HTTP response cannot create duplicate local admission.

BREAKING CHANGE: clients must send Idempotency-Key on job creation and retry.
```

## Atomic history
 
One commit should represent one coherent reviewable change. Separate unrelated formatting, dependency upgrades, generated output, and behavior changes. A commit should leave the repository in a valid state whenever practical.

Do not bunch unrelated subsystems into a monolithic commit, but strictly avoid artificial micro-commit fragmentation: do not artificially split a single logical unit of work (such as an implementation fix and its accompanying regression tests) across multiple single-file commits. Such micro-commits dilute Git history and complicate review. Keep a logical change and its direct tests together as a self-contained, reviewable atomic commit.

Merge commits generated by the hosting platform and Git-generated `Revert "..."` subjects are accepted by the validator. Pull-request titles must follow the normal format because they may become squash-merge commit subjects.

## Enforcement

- `.gitmessage` provides the local template.
- `.githooks/commit-msg` validates local subjects after running a setup script.
- `.github/workflows/commit-convention.yml` validates PR titles and committed subjects.
- `scripts/check-commit-subject.sh` is the single validator used by the hook and CI.
- `scripts/test-commit-subject.sh` has 21 regression checks: the 72/73/80/81/100-character
  boundaries, the previously blocked 73-character subject, formatting-only style subjects,
  and positive/negative format/exception rules. CI runs it before validating the actual PR
  title and complete commit range.

Run the same regression checks locally with:

```sh
./scripts/test-commit-subject.sh
```

Local hooks improve feedback but are not a security boundary; repository CI remains authoritative.
