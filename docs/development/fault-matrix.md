# Offline fault qualification

This is the executable regression map for the approved proposal's 25 numbered fault scenarios,
not a history of development audits or a live-provider acceptance result.

```sh
go run ./cmd/devtool fault-test
go run ./cmd/devtool check
go run ./cmd/devtool test-race
```

The [catalog](../../internal/devtool/fault-matrix.json) is the source of exact file/test identities.
It compares complete scenario text/order with [proposal section 23.2](proposal.md#232-required-fault-scenarios)
and runs 34 distinct nominated root tests with fresh `go test -json -count=1` evidence. Missing,
skipped or failed roots/descendants, incomplete packages, malformed output and exceeded budgets
fail. A green package with no matching test is insufficient. Full suites cover more than the catalog.

## Scenario scope

| Case | Required protection | Evidence boundary |
|---|---|---|

| FM06 | Unknown/new state does not invent success. | Provider-port observations, not live CLI compatibility. |
| FM07 | Stale poll cannot rewrite terminal state/events. | Fenced/current-handle rejection. |

## Interpretation and maintenance

Qualification reports compiler/platform and `25/25 passed-offline`; this is not 100% coverage,
a production service guarantee or live Kaggle verification. Source presence plus a test pass is
not proof that assertions are sufficient. Do not weaken scenarios/tests to get a green result.
The checker bounds events/output/diagnostics and invocation/package time; these are test limits,
not remote workload deadlines.

Keep the approved numbered scenarios and exact catalog identities consistent. Public/domain
requirements remain in [scope and requirements](scope-and-requirements.md); durable, state,
control and safety behavior is explained by the linked component guides, not old CI transcripts.
For real-host/provider gaps use the [operator checklist](validation-checklist.md) and
record observed results separately from these offline regressions.
